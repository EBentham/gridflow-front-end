## Findings

1. **major** `page.how_used[2]` ("Spotting a revised factor: silver keeps the newest fetch, bronze keeps each one.")
   - What is wrong: this lists a use that silver cannot deliver and that nothing the page points to can deliver either. Silver is overwritten on each transform, so it can never show that a factor changed. The notebook handle (`data.neso`, `data.sql`) reads silver only, and the page shows no route to bronze. Comparing earlier bronze files by hand is the only way, and the page does not say so. A reader is also told this is a use of the dataset with no evidence that NESO ever revises the factors.
   - Evidence:
     - Overwrite: `silver/neso/carbon_intensity.py:132-139` (reference read is `sorted(rglob("raw_*.json"), reverse=True)[:1]`), `:248-251` (`write_parquet(df, silver_dir / "intensity_factors.parquet")`), `storage/parquet.py:50-54` (temp file then `os.replace`). The author's statement that silver keeps only the newest value is true; the use built on it is the problem.
     - No silver route: `gridflow_models/research/handles/data.py:255` (`sql` runs against the local DuckDB store) and `handles/source.py:401` (`query` reads one silver relation).
     - No evidence of revision: the API definitions page example response (fetched 2026-10-06) is the same 14 numbers as the 26 Sep 2026 capture (Coal 937, Oil 935 ... French imports 53). `connectors/neso/endpoints.py:80` itself calls the table "Static". The author's own report says "no vendor evidence" for revisions.
   - Fix: drop the item, or say what is true and usable: "Checking whether a factor has changed means comparing bronze fetches; silver holds only the newest." Keep `raw_feed.note` as it is (it is accurate).

2. **major** `page.how_used[0]` ("Weighting a fuel mix into gCO2/kWh; `generation` needs gas and imports mapped first.")
   - What is wrong: a weighting built from `generation` silver cannot be exact, and the page does not say it is approximate. "Mapped" implies a lookup table is enough. It is not. (Judged major under the seat's rule on uses silver cannot deliver; a nit if the seat reads "mapped first" as flagging the gap.) The factors split gas into two cycles and imports into three countries; `generation` silver has one `gas` share and one `imports` share, and no silver table in `neso` holds the cycle or country split. A weighting from `generation` has to assume a factor: gas is 394 or 651, imports run 53 to 474 on the page's own chart, so the result depends on the assumption. The page does not say it is approximate.
   - Evidence (Polars, `C:\gridflow-data\silver\neso\`):
     - `generation`, `generation_current` and `generation_pt24h` all hold exactly `['biomass','coal','gas','hydro','imports','nuclear','other','solar','wind']`.
     - Factors minus generation: `['dutch_imports','french_imports','gas_combined_cycle','gas_open_cycle','irish_imports','oil','pumped_storage']`. Generation minus factors: `['gas','imports']`. The overlap is the 7 the author reports: `biomass, coal, hydro, nuclear, other, solar, wind`.
     - `silver/neso/carbon_intensity.py:559-585` (`_transform_generation`) keeps NESO's `fuel` and `perc` as sent, with no split.
     - The split does exist in `elexon/fuelhh` silver (`fuel_type`: `CCGT`, `OCGT`, `INTNED`, `INTFR`, `INTIRL`, plus interconnectors with no factor: `INTEW`, `INTNEM`, `INTNSL`, `INTIFA2`, `INTELEC`). The page lists that dataset in `related` but does not connect it to this use.
   - Fix, for example: "Weighting a fuel mix into gCO2/kWh. `generation` has one gas and one imports share, so a factor must be assumed; `elexon/fuelhh` splits both." Keep within the 12/14-word style the build enforces.

3. **nit** `page.how_used[1]` ("A per-fuel emissions lookup for merit-order or dispatch models.")
   - Silver does deliver a per-fuel lookup, so this is not a capability overclaim. But nothing in code, the vendor docs or the note names merit-order or dispatch use; the note's own Modelling notes say "approximate carbon intensity features". The page also tells the reader, two sections up, that the basis (combustion or life cycle) is unstated, which is exactly what a dispatch use would need. Suggest replacing with the note's own framing ("A static per-fuel factor lookup for approximate carbon-intensity features") or cutting.

4. **nit** `page.summary` and `page.facts.grain` (unit stated flat before the hedge)
   - The first line reads "The emission factor NESO's Carbon Intensity API assigns each fuel type, in gCO2/kWh", and `facts.grain` says "its factor in gCO2/kWh". Two sections later `what_it_is` and `record.fields.factor_gco2_kwh` say the response states no unit and gCO2/kWh is gridflow's label. The hedge is accurate (bronze body is bare integers: `bronze/neso/intensity_factors/2026/09/26/raw_20260926T174349Z_2dec0311.json`, 339 bytes; no `gco2` anywhere under `connectors/neso/`; label from `schemas/neso.py:52` and `docs/endpoints/neso.md:19`), but the hero reads as a NESO statement. A short "as labelled by gridflow" in the summary would remove the tension. Not blocking; the seat accepted the unit and basis wording.

5. **nit** `page.related[2]` (`elexon/fuelhh`: "Half-hourly generation in MW by Elexon fuel-type code")
   - Says what the dataset is, not how it relates (rubric section 6). It is the dataset that carries the gas-by-cycle and imports-by-interconnector split these factors need (finding 2). Suggest "Splits gas by cycle and imports by interconnector, as these factors do" (12 words).

6. **nit** `page.facts.cadence` ("The whole table per call; `sources.yaml` declares it weekly")
   - Accurate (`config/sources.yaml:626-629`: `schedule: "weekly"`, `max_query_days: 0`), but it is gridflow's fetch schedule, not how often NESO changes the table, and a file name appears in a public facts row. Could be misread as a weekly NESO update. Suggest "One call returns the whole table; gridflow's schedule fetches it weekly".
