## The headline findings

1. **Silver holds one direction per border, never both.**
   - `connectors/entsoe/client.py:40-49` `_FLOW_PAIRS` sends eight ordered pairs: GB-FR, GB-NL, GB-BE, GB-IE-SEM, FR-BE, FR-DE-LU, NL-DE-LU and NL-BE (in, out).
   - The reverse of each pair is never requested. The silver profile shows 8 `(in_area_code, out_area_code)` combinations, none of them the reverse of another.
   - So no border can be netted from this table, and the suggested "one border's two directions" chart cannot be drawn. The page says this in `what_it_is` and in the chart caption.
2. **`in_Domain` is the receiving zone.** This is a project check; the note quoted no ENTSO-E definition, and it said the opposite.
   - Rows with `in_area_code` GB track the positive (import-to-GB) part of Elexon FUELHH interconnector flows, 14 to 20 September 2026, hourly:
     - BE against `INTNEM`: correlation 1.000;
     - NL against `INTNED`: 1.000;
     - FR against the positive parts of `INTFR`, `INTIFA2` and `INTELEC`, per cable and summed: 1.000 (median absolute difference 7.7 MW);
     - IE-SEM against `INTEW`, `INTIRL` and `INTGRNL` summed: 0.94.
   - Against the net value instead, FR correlation falls to 0.952, with 37 hours where the ENTSO-E flow was above 50 MW while the Elexon net was below -100 MW. The per-cable sum explains the difference: one French cable can import while another exports.
   - The note had "flow from `in_Domain` to `out_Domain`" and labelled in=GB/out=FR as "GB → FR". Both are corrected in the note body (below).
   - The page always attributes the direction ("a project check against Elexon's interconnector flows"), and it never states it as an ENTSO-E rule.
3. **Physical, not scheduled.** `what_it_is` says so and names `commercial_schedules`, and `related` links it. `commercial_schedules` uses the same `zone_pair` style, so it requests the same eight ordered pairs (`endpoints.py:152-158`).

## Open questions

1. **Should gridflow request both directions?**
   - Adding the reversed tuples to `_FLOW_PAIRS` would let the table be netted, and would make the "one border's two directions" chart possible. This is a gridflow change, not front-end work.
   - The note's modelling line "Net interconnector flow = GB→X − X→GB" presupposes both directions. I left it and flag it here.
   - `commercial_schedules`, `net_transfer_capacity` and `dc_link_intraday_transfer_limits` share `_FLOW_PAIRS`, so they will have the same one-direction limit.
2. **The GB to IE-SEM series had missing hours** in the chart week (151 of 168 hours, and it ends at 10:00 on the 20th). I left IE-SEM out of the chart rather than draw a broken line. Whether this is a vendor gap or a local one is unknown, and the page says nothing about it.
3. **The GB-NL series** reads a steady 0.06 MW in many quarter-hours where Elexon `INTNED` is 0. This is harmless, but I don't know whether it is a vendor artefact.
4. **`published_at` code comments are wrong** (seat ruling 2). The `_published_at.py` module docstring calls `createdDateTime` "the vendor's genuine, leak-proof forecast issue time / publication vintage". For this dataset it is the response time, and it becomes `available_at` via the base coalesce. This needs a gridflow fix and is out of scope here.

## Template problems (reported, not worked around in shared files)

1. **The `---` ban against ENTSO-E EIC codes.**
   - `page_fields.py:379`, `:492` and `chart_spec.py:114` check the parsed value, so a `\x2D`-escaped EIC still fails in any text field, notebook cell or filter value. I tested this: `page.raw_feed.requests[0]: must not contain '---'`.
   - Only `group_map` keys can carry escaped EICs (per the seat's correction to ruling 1).
   - My workarounds:
     - the request URL shows the EIC dashes as `%2D`, a URL-equivalent form, and `raw_feed.note` says so;
     - the chart selects GB with a string range (`>= "10YGB"`, `< "10YGC"`);
     - the notebook uses `.str.startswith("10YGB")` and `.str[3:5]`;
     - the key `codes` read `out_Domain FR`, `BE` and `NL`.
   - Suggested fix: check only the raw front matter (the new `page_fields.py:596` check), and drop the parsed-value checks, which reject values that are safe once escaped.
2. **Detector em-dash rule.** The rule counts `--(?=\S)` inside EIC codes in the frame and notebook output. It is advisory and accepted under ruling 1. Suggested fix: skip `<code>`, `<pre>` and frame cells.
3. **At 390 px** the notebook tab label truncates to `cross_border_flows.ip…` (CSS ellipsis on `.nb-tab`, 218 px text in a 207 px box). This is template behaviour for long dataset names; nothing overlaps. The long `%2D` request also wraps at 390 with a blank gap before `&in_Domain`. It is readable, not clipped.
4. **There is no dark theme** (`tokens.css` and `theme.css` have no `prefers-color-scheme`). The "dark" screenshots are byte-identical to the light ones.
